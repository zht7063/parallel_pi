# parallel_pi：MVP 可行性与设计讨论

已收敛为 [MVP 设计规格 v0.1](mvp-spec.md)；本文件保留讨论依据。规格中的新增 D 默认值不视为已确认决策。

日期：2026-09-16。状态：讨论稿；双分支从属关系、文件记忆方向、同分支串行／跨分支并行模式、本地单用户 Web UI 范围及原版 pi 内核已由用户确认，本地/远端分支展示、session 节点及其操作、等待输入与失败排队规则、记忆查看纠正和开发成果操作也已确认；其余未确认建议不视为定案。

## 1. 用户目标

构建基于上游原版 pi 的可视化 agent harness，通过 Git submodule 引入内核，便于后续更新。

- 选择项目后，以列（未来可支持行）展示各 Git 分支的对话和开发记录。
- 用地图呈现各 Git 分支的工作进展。
- 点击会话继续工作，或从历史位置创建思路分支。
- 在 Git 分支末尾新建对话，继续该分支的工作。

本文将 pi 理解为原 badlogic/pi-mono（当前跳转到 earendil-works/pi），omp 理解为 can1357/oh-my-pi；若指其他项目，需要重新核实。

## 2. 可行性结论与证据

可行。现有内核已提供程序化集成基础，主要新增工作是代码工作区管理、会话关系、运行调度、持久化恢复与地图展示。

- pi 的 SDK 支持自定义界面、流式事件、会话管理及树状会话；当前会话替换接口位于 AgentSessionRuntime。见 [pi SDK](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)。
- pi RPC 提供会话切换、fork、clone、条目和树读取；fork 的默认语义是从指定历史用户消息分出，不应假定能在任意工具事件中间切开。见 [pi RPC](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md)。
- omp 官方介绍提供 SDK、stdio RPC 和会话能力，但不能据此认为它与 pi 的所有接口、文件格式和分叉语义兼容。其源码启动还涉及本地 Rust/N-API 构建。见 [omp](https://github.com/can1357/oh-my-pi)。
- Git worktree 可让同一仓库拥有多个工作目录；通常不允许同一分支同时检出到多个 worktree。见 [Git worktree](https://git-scm.com/docs/git-worktree)。

以上是文档核实，不是端到端验证。内核已选定 pi；固定具体提交后，还需通过集成探针验证恢复、分叉、取消与持久化。

## 3. 最关键的边界：对话历史与代码状态独立

已确认决策（2026-09-16）：Git 分支由行或列承载；每条思路分支归属于一个 Git 分支，一个 Git 分支可以包含多条思路分支。思路分支只表示对话上下文的探索路径，不对应独立代码版本。

**思路分叉复制/选择历史上下文，始终使用所在 Git 分支的当前工作区，包括已有未提交改动；分叉或切换思路不创建、切换或恢复代码版本。** 这是一项领域边界，而非仅为缩减 MVP 的临时处理。

例如会话 A 设计数据库，之后会话 B 修改了 schema。从 A 分出 A′ 后，A′ 的上下文来自 A，但看到的文件已包含 B 的修改。建议恢复/分叉时提示工作区的变化，并让 agent 重新读取相关文件。

记录 HEAD、diff 等信息仅用于追溯与提示，不使思路节点成为代码快照。未来若提供历史代码恢复，也应作为独立的代码操作设计，不附属于思路分叉。

需要隔离不同代码方案时，应通过新的 Git 分支表达；独立 worktree 与来源对话链接仍为实现建议。同一行或列内的所有思路路径共享该 Git 分支的当前代码，任一路径执行产生的文件修改会被其他路径后续执行看到。

## 4. 领域模型

| 概念 | 含义 | 建议关系 |
| --- | --- | --- |
| Project | 用户选中的仓库 | 拥有多个分支列；以仓库身份识别，兼容不同 worktree 路径 |
| BranchLane | 一列 Git 分支工作记录 | 独立 ID，记录 branch ref、worktree 路径与生命周期 |
| Conversation | 可打开的会话 | 属于一列，记录内核会话 ID、路径与来源 |
| ThoughtFork | 思路分叉关系 | 指向源会话及确切源 entry ID，保留当前叶子位置 |
| Run | 一次用户提交触发的 agent 执行 | 拥有状态、事件、错误、开始/结束时间及代码状态记录 |
| CodeObservation | 某次运行观察到的代码状态 | HEAD、dirty 状态、diff 摘要；不宣称是可恢复快照 |

“思路分支”指用户可见的上下文探索路径，不等同于模型内部推理过程。

已确认：一个地图节点代表一个普通 session，可持续多轮交流；继续该 session 不新增节点。“地图卡片”只是会话节点的可视化呈现称呼，不是额外领域对象；具体外观尚未确定。每个节点提供“新建接续会话”，列底部提供“新建独立会话”，后者没有隐含前驱，不把最近更新的会话自动当作主线。

会话接续与思路分叉用不同边类型表示。Git 提交/合并关系另行记录：Git merge 不自动合并两条对话上下文；会话关系图也不是 Git commit 图。

内核原生会话树与产品的跨会话地图应保留映射，不能只用标题、时间戳或分支名定位对象。MVP 可优先将每次用户分叉映射为独立原生会话，以减少多个路径共用活动游标的复杂性，具体能力由探针确认。

## 5. 已确认的会话操作语义

| 操作 | 上下文 | 代码 |
| --- | --- | --- |
| 打开会话 | 只查看记录 | 无变化，不启动 agent |
| 继续会话 | 恢复选定路径的末尾，再提交新消息 | 当前分支工作区 |
| 从此处分叉 | 保留指定位置之前的有效上下文，建立新路径 | 当前工作区；无历史回滚 |
| 新建接续会话 | 在所选节点后创建新 session，记录接续边，通过文件记忆按需获取背景 | 当前分支工作区 |
| 新建独立会话 | 在列底部创建无前驱的根节点，通过文件记忆按需获取背景 | 当前分支工作区 |

已确认以文件记忆支持后续会话选择性读取，不再以自动注入前序摘要作为默认建议。建议启动时只提供记忆入口和少量索引，具体召回协议见 [文件记忆设计](./memory-design.md)。继续原会话和历史分叉仍保留各自的原生上下文语义。分叉点必须是内核支持且消息/工具调用配对完整的位置，UI 不开放不可执行的节点。

## 6. MVP 范围（部署形态已确认）

已确认：首版为本地单用户 Web UI，管理本机 Git 项目。用户在本机启动后端，通过本机浏览器访问；agent、Git 操作和文件读写均在本机执行。项目选择器使用后端访问本机目录。

MVP 不包含多人账户、团队权限、远程工作节点或公网部署。建议服务默认仅监听 loopback；具体启动命令、端口与项目选择交互待实现时确定。本地执行不限制调用用户配置的云端模型 API，也不承诺离线推理。

必须形成以下闭环：

1. 添加/选择本地 Git 项目，展示本地分支；仅远端存在的分支以较窄的行标识并提供“拉取到本地”按钮；支持创建新的 Git 分支。
2. 已确认保留并使用已有工作区的未提交修改；其他分支按需准备独立 worktree，不自动搬运改动。复用已有 worktree 时检查占用，不强行重复检出。
3. 列内显示会话地图，支持打开、继续、分叉和新建接续会话。
4. 展示模型回复、工具调用、错误和运行状态，支持停止运行；首版输入支持文字和图片，管理应用创建的 session，历史导入与删除暂缓。
5. 已确认：同一 Git 分支内串行，不同 Git 分支之间并行。每列一条执行队列，分支内所有思路共用队列，同一时间最多一个 run 执行；其他提交排队，查看历史和编辑待发送消息不受影响。
6. 页面刷新和服务重启后恢复历史与图关系；浏览器断开不等于取消任务。
7. 提供 diff 查看和用户明确触发的代码提交；首版合并由外部 Git 工具完成。HEAD、dirty 与任务完成状态分别展示；不把会话完成视为提交或合并。
8. 固定目录保存会话变更记录、结论和持久偏好，后续会话按需读取；用户可查看、纠正记忆，写入失败明确提示。重试方式仍为实现建议。

暂缓：双内核同时支持、自动多 agent 调度、多人协作、远程执行、完整 IDE、自动合并与冲突解决、对话语义合并、历史文件精确回滚、任意位置图编辑、复杂 Git 拓扑布局。

### 已确认的执行模式及调度建议

- 调度边界是 Git 分支，不是思路或浏览器页面；切换会话、打开多个页面不会增加该分支的执行名额。
- 不同 Git 分支可同时运行，各自在独立工作区执行；不使用覆盖整个项目的单一执行锁。
- 建议首版按提交顺序执行，允许取消尚未开始的任务。任务真正开始时检查当前代码和相关记忆，不能把入队时观察到的文件视为最新状态。
- 前一个 run 完成或停止且工具执行已收束后，才能释放分支执行名额；点击停止不代表可以立即开始下一个任务。
- 已确认：等待用户回答时保留该分支执行名额，失败后暂停该列队列；其他列不受影响。这里的等待指运行中 agent 提问等待回答，正常回复完成后的空闲不占用执行名额。建议异常中断也暂停该列；恢复、重试及跳过操作的具体交互仍待细化。
- 已确认全局并发默认 2，可配置，不改变分支内串行、分支间可并行的规则。
- 已确认停止后暂停该列；每个 run 入队时固定模型，之后修改默认值不改变已有排队任务。

## 7. 地图如何表达进度

用户提出全局地图占据页面主体：单击 session 展开右侧详情，双击进入会话。专注会话视图将地图缩至左上角；单击缩略图打开地图面板，双击返回全局。左下角提供 pi 图形化配置入口，其上方提供项目添加/切换区，新项目排在底部紧邻设置，旧项目上移。详见 [地图与会话交互](./ui-interaction.md)，其中预览/工作分离、应用内地图浮层、浏览位置与草稿保留，以及双击和显式按钮并存已确认；其余补充仍标为建议。

Git 分支列内建议采用自上而下的会话树；详情摘要和完整会话分层展示，具体视觉样式尚未定案。

- 卡片：标题、当前状态、最近活动时间、简短结果、是否有代码改动。
- 运行状态：queued / running / waiting_input / succeeded / failed / cancelled / interrupted。
- 任务状态：待办 / 进行中 / 待验证 / 完成，由用户明确标记；agent 一轮结束不代表任务完成。
- 代码信息：HEAD、dirty、变更文件数；测试状态只展示实际执行证据，并关联当时代码，代码再变化后标为过期。
- 地图默认折叠历史、自动布局，保留节点位置稳定性与清晰选中状态。

不使用没有验收清单支持的“完成 73%”。运行、完成、错误等状态必须同时有文字标识。

## 8. 内核集成与 submodule

已确认：首版采用上游原版 pi（earendil-works/pi，原 badlogic/pi-mono），通过 Git submodule 引入。选型依据为会话树 RPC 与地图需求贴合、MWF 已有 pi 接入路径，以及源码集成所需工具链；这不是性能或稳定性实测结论。具体提交和 RPC / SDK 接入方式仍待验证。详见 [pi / omp 选型分析](./engine-comparison.md)。

建议结构：Web UI → 本地后端（项目、地图、调度、事件存储）→ EngineAdapter → 内核子进程。Git/worktree 管理由后端单独负责。

MVP 可优先验证 stdio RPC：独立进程便于设置 cwd、追踪退出与停止。若选定版本 RPC 缺少必要树操作，再采用运行于独立 worker 进程的 SDK。不要解析 TUI 输出作为正式协议。

分支执行队列由 parallel_pi 后端持有；内核的 steer/follow-up 队列服务于单个会话，不能替代跨思路的分支调度。停止操作需同时考虑内核待执行消息和子进程，避免取消后继续执行排队内容。

适配器仅暴露实际需要的能力：创建、恢复、读取历史、分叉、提交、订阅事件、停止与销毁。记录能力标记，避免假定 pi/omp 可互换；前端不直接依赖上游事件形状。

子模块放在例如 vendor/pi，固定具体 commit；从该检出构建/启动内核，避免运行时误用全局安装版本。上游更新流程是：更新子模块 → 安装固定依赖并构建 → 兼容性检查 → 提交新的指针。submodule 不会自动解决破坏性 API 变更或会话格式迁移。

每个会话记录 engine 类型及 revision。升级前备份原生记录，验证旧会话可打开和继续；不能假定升级后的记录能被旧版本再次读取。尽量通过适配器/扩展集成，减少内核补丁。

## 9. 持久化、并发与权限

- 建议 SQLite 保存项目、列、关系、run 与有序事件；原生会话记录由内核维护，应用保存稳定映射。原生记录是上下文权威来源，应用库是产品关系/调度的权威来源。
- 原生会话文件和应用库不是一个事务；创建与分叉需有操作 ID、失败状态和启动时对账，避免“地图有节点但会话不存在”。
- 每次提交携带 request ID，后端防止双击和断线重试导致重复执行；事件有单调序号，重连补发并去重。不要为恢复画面重新执行工具。
- 后端而非页面持有运行状态及 worktree 锁。终止需处理子进程、取消超时与最终状态；取消不撤销已发生的文件修改。
- 已确认关闭网页不停止任务；后端重启将未完成 run 标为 interrupted，由用户决定如何继续，不自动重放命令。
- worktree 只隔离工作目录，不是权限沙箱；共享 Git refs、机器端口、数据库和外部服务仍可能冲突。应用锁也不能阻止外部编辑器/终端写入，应检查外部 HEAD/工作区变化。
- 不自动丢弃 dirty 文件，不默认执行 reset --hard 或强制删除 worktree。归档会话与删除代码工作区分开处理。
- 本地 MVP 默认仅监听 loopback，校验 Origin/Host，并保护写操作和流连接；凭据仅后端可访问，限制日志泄露，渲染工具输出和 Markdown 时过滤不可信 HTML。
- pi 官方说明其不内置文件/进程/网络权限限制；需要更强边界时须由宿主提供沙箱，不能把 UI 按钮当成隔离机制。见 [pi 权限说明](https://github.com/earendil-works/pi#permissions--containerization)。

## 10. 实现前先做的验证与验收

先做一个小型内核探针：固定 revision，在指定 cwd 创建会话、输出事件、恢复、分叉、取消，再重启读取。验证分叉点是否包含选中的消息、压缩后的历史如何处理，以及取消时工具子进程是否退出。

随后再实现后端持久化/调度、分列界面与地图。验收至少包括：

1. 两个 Git 分支同时修改同名文件，改动各自留在对应 worktree。
2. 同一 Git 分支的两个思路提交后，后者排队；前者结束且工具已收束后才能开始，能看到前者留下的代码修改。多个浏览器页面仍遵守同一队列；其他 Git 分支可以同时执行。
3. 从 A 分出 B 后，A 历史仍可查看；B 的上下文不包含分叉点之后的消息，但使用当前代码并保留未提交改动；分叉及切换思路不创建 Git 分支、不切换 HEAD、不恢复文件。B 执行产生的修改可被 A 后续执行看到。
4. 继续 session 仍是原节点；新建接续会话有明确前驱；列底部新建独立会话没有前驱。读取的记忆及代码工作区可追溯，不用注入完整前序聊天也能按需取得已保存结论。
5. 刷新页面不丢记录或重复执行；后端异常重启显示 interrupted。
6. 取消后不再接收该 run 的新工作，已发生修改仍可查看。
7. 分支被外部切换/删除或工作区变脏时，不静默把任务发送到错误代码状态。
8. 升级一次内核后，已有会话仍能打开、继续和分叉。
9. 本地分支可见；仅远端分支以紧凑行显示并可拉取；新建分支后显示对应列。
10. agent 等待回答时同列后续任务不启动；run 失败后同列暂停，其他列仍能执行。
11. 记忆可以查看和纠正；写入失败可见，不误显示保存成功。
12. 用户可查看 diff 并明确触发提交；会话结束不自动提交，首版不提供内置合并。

## 11. 优先讨论的问题

已确认：思路分叉采用“历史上下文 + 当前代码”，不对应代码版本，详见第 3 节。

1. 执行模式已确认：每个 Git 分支内部串行排队，不同 Git 分支并行。等待回答占用执行名额、失败暂停该列已确认；停止后暂停、入队固定模型及全局并发默认 2 已确认；剩余细节包括恢复/重试交互和异常中断处理。
2. 文件记忆及项目偏好管理已确认沿用 MWF 的设计思路，不再另设偏好共享政策。Git 跟踪沿用 MWF 策略并区分共享/私有记忆和完整聊天；实现阶段仍需确定多 worktree 的存储与读取方式，以及运行时复用方式；目录名尚未固定。
3. 内核已确定为原版 pi；下一步验证并固定具体提交，确定原生 RPC 或 SDK worker 接入方式。

## 12. 分支与成果操作：已确认范围及待细化建议

- 已确认展示本地分支；对本地没有但远端存在的分支，用较窄的行标识，提供“拉取到本地”按钮。具体放在分支列表还是地图附近尚未确定，不擅自将用户要求改为完整分支列。
- 已确认该按钮命名为“拉取到本地”：将所选远端分支拉取为对应的本地分支，完成后显示本地分支列，供用户开始会话；不向当前分支自动合并。建议实现时建立对应跟踪关系，工作区准备完成后允许执行。远端列表刷新、同名分支和多个 remote 的处理仍待细化。
- 已确认支持创建新的 Git 分支。建议创建时填写分支名并选择起点，工作区准备完成后才允许执行任务；具体起点默认值待定。
- 已确认支持 diff 和明确触发的提交，合并暂由外部 Git 工具完成。建议提交前显示文件范围及提交信息，并与该分支 agent 执行互斥；提交文件选择、推送以及分支归档/删除尚未定案。

## 13. 已确认的补充边界

主要布局和操作已足以整理 MVP 规格。以下五项已由用户确认；具体集成机制仍待验证。

| 主题 | 讨论范围 | 已确认方案 |
| --- | --- | --- |
| 工作区接入 | 已有分支有未提交改动或已被检出时，如何开始任务 | 保留并使用已有工作区的未提交修改；其他分支按需准备独立工作区，不自动搬运改动 |
| 运行生命周期 | 浏览器关闭、后端退出、停止、失败后的行为 | 关闭网页任务继续；后端重启将未完成 run 标为中断，由用户决定如何继续，不自动重放工具。停止后的队列行为仍待细化 |
| 文件记忆落盘 | 是否纳入 Git、是否直接复用 MWF | 沿用 MWF 的跟踪策略，区分共享记忆、私有记录与完整聊天；运行时复用方式另行验证 |
| 模型设置范围 | 默认配置修改对已有/运行中 session 的影响 | 设置统一管理 API key 等连接信息；项目及会话可各自选择模型；默认设置与当前会话模型分开，不悄悄改变运行中任务 |
| 首版输入与整理 | 文本、图片、附件；历史会话导入、归档与删除 | 首版支持文字与图片，先管理应用创建的 session；历史导入与删除暂缓，归档方式尚待细化 |

已确认项目切换保留每个项目的浏览位置和草稿，原项目后台任务继续，项目入口显示运行中／等待回答／失败。全局并发上限仍可在实现阶段配置。

具体颜色、尺寸、动画、列表溢出、重复添加处理等可在草图阶段收敛；pi 固定版本、RPC/SDK 以及持久化技术通过集成验证决定，不需要逐项向用户询问技术偏好。
