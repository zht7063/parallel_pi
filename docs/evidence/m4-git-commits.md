# M4e3：应用内 Git 提交与恢复

本阶段将 M4e2 原生事务接入应用持久任务、HTTP 和分支变更界面。用户选择整文件，查看实际提交树，再明确创建本地提交。提交请求身份绑定修订、树、路径和消息；同请求重试不重复运行钩子或创建提交。

## 行为与恢复

- 提交意图和第一项操作同一 SQLite 事务保存；pending/uncertain 阻止同分支新执行。
- 真实钩子开始、结束、退出状态进入持久事件；刷新页面后重新打开变更面板可继续查看。
- 文件改变使旧预览失效；钩子拒绝提交保留消息与选择，未选部分暂存保持不变。
- 重启与显式恢复先核验同分支全部旧进程均已收束，再核对原事务；不自动重放提交。
- 外部移动 ref 后不会盲目修复。用户明确确认外部核对可保留当前 Git 状态，记录 reviewed 和原不确定原因；只移除本事务拥有的锁，未知锁仍拒绝处理，队列保持暂停。
- 公共任务 DTO 不暴露私有事务目录。

## 验证

`npm run check` 通过架构、类型、格式检查和全部 55 项 Node 测试。`npm run build` 通过；完整 `npm run test:browser` 10 项通过。严格 UI 审查 0 errors / 0 warnings，结果见 `m4-git-commits-ui-audit.json`。已人工查看 `test-results/git-commit-confirm-narrow.png`：390px 下实际 diff 换行，最终确认按钮可达。

新增应用测试验证真实钩子占用分支、请求去重、提交确认丢失后的重启恢复、旧 worker 未收束时禁止恢复，以及外部 ref 变化后显式核对保留 index/ref 和原错误。浏览器验证过期预览、钩子失败保留输入、运行中刷新、只提交选中文件、未选部分暂存不变、消失选择可移除及外部核对确认流程。

## 验收边界

应用重启测试模拟提交响应丢失；真实中断原生提交 worker 的证据在 M4e2，不能将二者描述成应用提交期间真实后端 SIGKILL 的完整端到端用例。该故障组合及完整 A01–A16 验收继续在 M5 核对。既有普通 Git inspect/validate 路径的进程监督范围也需在 M5 审计。备份、本机 Linux 打包、手动升级仍待实施，本阶段不代表整个 M4 或 MVP 完成。
